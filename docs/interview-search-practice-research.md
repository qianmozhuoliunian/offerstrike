# 面经搜索与 AI 复习：开源项目调研

调研日期：2026-11-12。目标是为面经搜索和 AI 日常复习重新设计提供参考。以下依据项目 README 和可公开查看的源码整理，**没有安装运行这些项目，也没有实测平台召回率、反爬行为、追问质量或接口稳定性**；README 中的功能描述不等于本项目已经具备这些能力。

## 先区分三类能力

1. **发现来源**：根据岗位、公司和其他条件找到可能相关的原帖链接，可能依赖通用搜索引擎，也可能使用站内搜索。找到链接不代表能读取正文，也不代表结果已核实为真实面经。
2. **读取和核对**：打开或解析已发现的链接，保留来源、原文片段和日期依据；失败或信息不足时明确提示，而不是用摘要冒充正文。
3. **用于复习**：从用户确认的题目和来源出发练习，AI 基于题目、用户回答和必要上下文追问或反馈；追问不能被标成原帖真实提问，未评估不等于不会。

这些区分与现有 [DESIGN.md](../DESIGN.md) 的来源可追溯、日常复习和模拟面试分离等原则一致；具体交互仍需要用户确认。

## 面经来源和搜索

### InterviewRadar

[InterviewRadar 官方仓库](https://github.com/KunChen1110/InterviewRadar) 的 README 描述：先通过宿主的 WebSearch 发现牛客或公开网页 URL，按域名分发给连接器读取，再检查题目对应的原文证据与时效，之后去重、排序。它将牛客、GitHub 题库、知乎及其他可读网页分开处理；覆盖效果取决于公开网页可访问性和搜索发现能力。小红书采用可选的 MediaCrawler 接入，需额外配置登录；README 区分只读文字的 fast 和包含图片 OCR 的 deep 模式。

**可以借鉴**：搜索、正文读取、题目提取分别显示状态；未读到原文时仍可展示原链接，但不要宣称已核实题目。多篇相似题可聚合，同时保留各自来源和原话。**边界**：以上是仓库自述与其工作流，不代表本地已接入 WebSearch、MediaCrawler 或小红书，也不代表检索结果已经过独立真实性核查。

### 面经猎手 interview-experience-spider

[牛客采集源码](https://github.com/bcefghj/interview-experience-spider/blob/main/scrape_nowcoder.py) 中，`search()` 向牛客搜索接口发送关键词、面经标签和分页信息，再根据结果类型分别读取 Feed 页面或 Discuss 正文，并按标识去重。它是站点特定的实现，不是通用搜索引擎；接口变化、限流和实际可用性均未实测。

[项目 README](https://github.com/bcefghj/interview-experience-spider) 描述另一条小红书路径需要 Cookie 和签名依赖；[小红书采集源码](https://github.com/bcefghj/interview-experience-spider/blob/main/scrape_xhs.py) 中 `search_notes()` 进行关键词搜索，`fetch_note()` 请求笔记详情。源码中得到的文字内容不意味着图片中的面经已读取完整。部署与代码复用前应核对上游许可和平台规则，不能把示例视为稳定的官方公开 API。

**可以借鉴**：为牛客等站点单独记录发现、正文读取和降级状态；保留站点 ID 和原帖链接，便于去重与回查。无需把某个站点接入成功外推为所有来源均可搜索。

### Interviews_Helper

[Interviews_Helper 官方仓库](https://github.com/wh21hw/Interviews_Helper) 在支持范围表中区分：小红书关键词发现使用用户手动登录的 Chrome，并支持图片 OCR；牛客、知乎、微信公众号是提供具体 URL 后读取正文，**没有对应的站内关键词搜索器**。它也列出失败原因与断点续跑，不自动处理验证码。

**可以借鉴**：按来源展示“可以搜索”“需提供链接”“需要登录”或“读取失败”等真实能力与状态，而非简单堆砌来源名称。

## AI 复习与追问

### Open Interview

[Open Interview 官方仓库](https://github.com/yeyimilk/open-interview) 的 README 描述导师和面试官两种模式：前者侧重围绕材料交流，后者根据回答进行逐轮评价和追问；其题目生成描述中包含引用及 `follow_up_axes`，以支持对实现细节、权衡和故障处理等方面深入询问。这是项目自身描述，未在此调研中运行验证。

**可以借鉴**：每次只呈现一题，追问明确关联用户刚才说过的内容；如题目源自面经，保留原帖链接和原文依据，AI 新生成的追问单独标注。围绕代码和简历的能力不应默认为本项目现有能力，也不应未经用户选择读取简历。仓库 README 对许可证文件仍有待补充的说明，复制代码前需单独核对授权。

### AI Mock Interview Coach

[AI Mock Interview Coach 官方仓库](https://github.com/steph-xue/ai-mock-interview-coach) 的 README 描述练习模式会提供与岗位和个人材料相关的提示，模拟模式则减少提示以接近真实面试；结束后可按题查看原回答与改进建议。其实现说明是让模型按三道主问题、每题一次自适应追问进行，但追问顺序仍由模型决定；README 将应用侧强制阶段控制和断线恢复列为后续改进。

**可以借鉴**：让用户选择先获得帮助、补充回答或继续，而不是只给一次笼统评价；提供可对应具体回答的改进建议。该项目以实时语音和 AWS 服务为基础，不能据此认定本项目需要直接照搬该架构，也不把其评分当成客观能力结论。

## 对本项目的建议，待讨论

1. 先明确搜索结果的用途：用户是在找原帖、想从真实来源整理题目，还是希望直接开始练习；围绕来源、证据、时间和相关性设计结果，而非只增加站点下拉选项。
2. 为每个候选来源记录发现方式、内容读取能力、登录或额外配置需求、失败提示和实际验证结果。现有搜索服务作为基线；候选来源及其范围应由用户确认后逐一验证。
3. 将日常复习设计为题目来源 → 用户回答或求助 → 针对回答的反馈与必要追问 → 用户选择继续、重答或跳过。追问是否即时、提示何时出现以及用户最不喜欢现有流程的哪一点，仍待沟通。
4. 在真实页面抽样检查不同岗位、来源和日期，衡量可用原帖数量、相关性、重复、可访问性和日期可信度；练习部分检查不知道答案、信息不足、服务失败和用户纠正 AI 的情况。没有实测前不承诺覆盖率或效果。
